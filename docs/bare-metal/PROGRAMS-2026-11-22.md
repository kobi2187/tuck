# Three programs on real parts: what they showed (2026-11-22)

Three device programs, written against off-the-shelf parts with datasheet
values, to test the bare-metal designs on code someone would actually ship:
is it beautiful, where does it rub, does it work. They live in
`tests/metal/devices/` and are pinned by `tests/suites/device_programs.nim`.

| Program | Parts | Lines |
|---|---|---|
| **Irrigation controller** (`irrigation/`) | STM32F103C8T6 "Blue Pill"; Maxim DS3231 RTC (minute alarm on INT/SQW); YF-S201 Hall flow meter (450 pulses/L) counted by TIM2 in hardware; TowerPro MG996R servo turning a 1/2" ball valve (50 Hz, 1000/1500 us) | 581 |
| **MP3 voice recorder** (`recorder/`) | STM32F103C8T6; VLSI VS1063a on the SparkFun VS1063 Breakout (BOB-11684), MP3 encode and decode; microSD over SPI (raw blocks); Bourns PEC11R-4215F-S0024 encoder on TIM4; three buttons on EXTI | 903 |
| **Radio-controlled quad** (`drone/`) | SpeedyBee F405 Mini (STM32F405, ICM-42688-P); SpeedyBee BLS 35A Mini V2 4-in-1 ESC (DShot600); RadioMaster RP1 V2 ExpressLRS receiver (CRSF, 420 000 baud); T-Motor F1404 3800KV on 3" props | 667 |

Sources for the numbers: VS1063a datasheet v1.33 (§10.8 SCI registers, §11.6
encoding procedure, `endFillByte` at 0x1e06); DS3231 register map; YF-S201
F = 7.5 x Q; MG996R pulse range; CRSF frame format (crsf-wg wiki, ExpressLRS);
DShot frame and timing (Betaflight docs); ICM-42688-P bank-0 addresses as the
Linux `inv_icm42600` and ChromiumOS `icm426xx` drivers define them. Where a
fact could not be confirmed, the code says so (the SpeedyBee Mini's motor
timer mapping).

## How each is built

The same split in all three, and it is the main lesson: **a pure module that
makes every decision** (`schedule`, `session`, `flight`), and **device code**
(registers, polled drivers, interrupt handlers, an actor holding state) that
does nothing but move data between the hardware and the pure module. The pure
module runs in a host simulation on all three backends; the device code is
checked.

| | Simulation (Nim, Odin, D, byte-identical) | Device code |
|---|---|---|
| Irrigation | a week, minute by minute: a dry Wednesday and a leaking Friday; 222 L delivered | checks; the RTC alarm is a `[signal]` handled by `actor Garden` |
| Recorder | 3 s of 128 kbit/s MP3 into 94 blocks, an odd last byte via `endFillByte`, played back byte-exact; SCI_VOL 0x0E0E for -7 dB | checks; three buttons raise one `[stream]` event |
| Drone | CRSF with line noise and a corrupt frame (2 good, 1 bad); arm, a 335 deg/s roll held at 319 after 0.9 s; link loss disarms and stops the motors; DShot frame 33478 for 1046 | checks; UART bytes are a `[stream]`, the gyro's data-ready a `[signal]`, one `actor Flight` |

`tuck audit FILE --events` prints each program's whole interrupt surface in
six to ten lines: what is raised, by which handler, how it is delivered, who
handles it.

## What was beautiful

- **Decision tables carried the policy.** The valve's table made every
  combination of (due, open, quota met, flowing, faulted) a written row; the
  arming table did the same for the drone. Reviewing the policy is reading
  the table.
- **The simulation found a real policy bug, and the table made the fix
  complete.** The first irrigation table re-opened the valve the minute after
  a dry-supply alarm, so it flapped open and closed all morning. Adding a
  `faulted` column forced a decision for every row that touches it.
- **The transitions table found a real code bug.** The recorder's first
  `endPlayback` set `mode = Idle` from any mode; Recording -> Idle is not an
  edge, and the checker refused it. Stopping that way would have abandoned an
  unfinished MP3 file.
- **Errors made every timeout visible.** Every I2C/SPI wait is bounded and
  returns an error; the checker refused the one result I forgot to read
  (`acknowledgeAlarm`).
- **Delivery kinds read like the hardware.** `Byte({data, at}) [stream,
  overflow: drop_newest]` and `GyroReady() [signal]` say what an embedded
  engineer would write in a comment, and the checker holds them to it.
- **One registry per module** was right the first time it applied: the drone's
  two interrupt sources are one `FcEvents` with two events, which reads better
  than two registries.

## What did not work yet (blockers)

1. ~~**Actors do not build freestanding.**~~ **Fixed 2026-11-23** (bare-metal
   roadmap 2.0): a ring mailbox per actor, drained by the stackless
   scheduler. The irrigation and recorder programs now build for the board
   (30 KB and 44 KB of flash) and, under QEMU with no RTC or SD card on the
   bus, exit 1 through their bounded waits. The irrigation actor costs 52 B
   of RAM in all. The drone waits on item 3.
2. **`bind` does not exist** (expected: bare-metal 2.2). Each `main` polls the
   pending flags and calls the `[irq]` fn by hand; the deferred delivery the
   kinds promise is not built either, so today those handlers run inside the
   (polled) interrupt.
3. **DMA cannot be expressed.** DShot600 reloads a timer compare register
   every 1.67 us from a buffer, which needs the buffer's address handed to a
   DMA stream. Tuck has no address-of for a buffer it owns (pointers exist only
   at the extern boundary), so motor output is an extern. Any DMA peripheral
   (SPI to the SD card, I2S audio, ADC sampling) meets the same wall. **Needs
   an owner ruling: a DMA buffer as a declared, statically placed object.**

## Frictions, worst first

| # | Friction | Seen | Fix direction |
|---|---|---|---|
| F1 | No `?` propagation: each fallible call costs three lines (`let r = ...`, `if not r.ok:`, `err r.err`). `readBurst` in the RTC driver is 25 lines of guards around 6 operations | all three | a propagation operator (the overview says there is none, on purpose: this is the evidence to revisit) |
| F2 | Domain words are reserved: `byte`, `addr`, `out`, `from`, `block` (backend keywords, TK-PA12) and `select`, `on`, `pending`, `error`, `none` (Tuck keywords). Ten collisions in three programs; `error` in a PID and `byte` in a UART driver hurt most | all three | mangle backend keywords in params and fields instead of refusing them; the Tuck keywords are by ruling |
| F3 | Fallible fns must be `[io]`, but register access is not I/O, so every driver fn also gets "remove `[io]`" (TK-EF02). The two rules contradict each other | all drivers | let `!T` stand alone, or count register access as an effect (`[mmio]`) |
| F4 | No bitwise operators. Masks and shifts became `% 2^k`, `/i 2^k`, `* 256`; XOR (CRSF CRC-8, DShot checksum) needs `std/bits` calls | drone | operators, or at least `xor` |
| F5 | Register field types: single bits are `bool` (good), wider fields `u32`; an `int` needs `~u32`, and a named constant must be declared `const x: u32` though a literal needs nothing | all three | let an integer constant fit a field the way a literal does |
| F6 | No call inside a payload (TK-PA13): about 25 extra `let`s. Often clearer, but in arithmetic-heavy code (PID, mixer) it doubles the line count | drone, recorder | keep; maybe allow pure calls |
| F7 | A cast before an operator parses as a type (`x ^f64 * y` is a type product); float literals refuse a redundant cast, yet `if armed: e else: 0.0` makes `0.0` an f64 | drone | precedence fix; literals typed by the other branch |
| F8 | `[w1c]` is not built: EXTI_PR is declared as one full-width field so a write is a plain store, never a read-modify-write that clears other lines | all three | D3, ruled |
| F9 | One register block per instance (SPI1 and SPI2 written out twice) | recorder | D12, ruled |
| F10 | A `[signal]` handler cannot see the count its repeats merged into | design | give a signal handler the count, or document why not |

## Compiler bugs found (pinned in `known_bugs`)

- **A119** a bare record literal in a list returned as `Seq[T]` passes the
  checker and fails the Nim build. Open (ruling as A49: refuse, TK-TY45).
- **A120** `var m: M = M.Idle` loses the variant, so a sealed transition out
  of it is refused; without the `: M` it checks. Open.
- **A121** a match with a void-call arm and a `return` arm was refused ("void
  vs unit"), though `if` allowed it (#148). **Fixed** (`unifyArmType`).
- **A122** `f with {values: []}` is refused for lacking an element type,
  though the field gives it one. Open.

## Verdict

The design holds up on real hardware code: decision tables, transitions,
error results and the event declarations each caught or prevented a real bug
in these three programs, and the event report is the interrupt documentation
embedded teams usually keep by hand. What stops the programs is not the
design but three missing pieces: actors on metal, `bind` with deferred
delivery, and a way to give DMA a buffer. Then F1-F3, which every driver pays
for on every line.

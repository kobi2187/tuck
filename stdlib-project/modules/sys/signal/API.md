# sys.signal

## Purpose
A portable abstraction over POSIX-style signal delivery: register handlers or receive a stream of incoming signals, enabling graceful shutdown and cooperative cancellation instead of relying on default-terminate behavior or unsafe in-signal-handler logic.

## Design lineage
Modeled on Rust's `signal-hook` crate — chosen over raw `sigaction` specifically because `signal-hook`'s central insight (move all real handling logic *out* of the async-signal-unsafe handler context and into ordinary code that merely observes "a signal arrived") is exactly the safety property a stdlib abstraction should bake in by construction. Go's `os/signal` (a channel that receives delivered signals, consumed by ordinary goroutine code) is the secondary model for the channel-based API shape. Raw POSIX `sigaction` is the capability floor this must cover (register per-signal, be able to restore default disposition) without exposing its handler-context unsafety directly.

## Proposed API
```
enum Signal { Interrupt, Terminate, Hangup, Quit, User1, User2, /* platform-available subset */ }

struct SignalReceiver { .. }        // implements a Reader-of-Signal-shaped consume, or exposes recv() directly
fn register(signals: &[Signal]) -> Result<SignalReceiver, SignalError>;
impl SignalReceiver {
    fn recv(&self) -> Signal;                          // blocks until a registered signal arrives
    fn try_recv(&self) -> Option<Signal>;               // non-blocking poll
    fn recv_timeout(&self, d: Duration) -> Option<Signal>;
}
// composes with sys.sync/sys.thread: a dedicated thread can block on recv() and
// forward shutdown into whatever cancellation mechanism the app already uses
// (an sys.sync channel send, a shared AtomicBool, or std.async's cancellation context).

fn ignore(sig: Signal) -> Result<(), SignalError>;       // explicitly ignore, e.g. SIGPIPE on a socket-heavy server
fn restore_default(sig: Signal) -> Result<(), SignalError>;

// Low-ceremony convenience for the single most common case:
fn on_interrupt() -> SignalReceiver;   // shorthand for register(&[Signal::Interrupt, Signal::Terminate])
```

## Key design decisions
- There is no callback/handler-function registration API at all — only a receive-oriented `SignalReceiver` that ordinary (non-signal-context) code polls or blocks on. This closes off the entire class of "did unsafe things in a signal handler" bugs (calling a non-async-signal-safe function like `malloc` from inside a handler, a classic real-world footgun this design refuses to expose) by construction, at the cost of a small, bounded delivery latency versus a true synchronous handler — judged the right tradeoff since every validating app's use case is "shut down gracefully soon," not "respond within microseconds."
- `recv()` returns an owned `Signal` value through an ordinary channel-like interface rather than the caller registering a `fn(Signal)` pointer, so `sys.signal` composes with `sys.sync`/`sys.thread`/`std.async` the same way any other producer of values does (Principle 3) — a signal-watcher thread is just another thread sending into whatever coordination primitive the app's shutdown logic already uses, no signal-specific glue required.
- `ignore(Signal::...)` (e.g., silencing `SIGPIPE` so a broken socket write returns a normal `IoError` instead of killing the process by default disposition) is a first-class, explicit function rather than left to platform-specific incantations scattered through app startup code — a direct, common need for exactly the kind of long-lived network servers this stdlib targets.
- Registering the same signal from `register()` more than once (e.g., both a top-level shutdown watcher and a library dependency wanting the same signal) is explicitly specified to fan out to all active `SignalReceiver`s rather than the second registration silently stealing delivery from the first — avoiding a surprising "only the last registrant gets called" trap.

## Validated by applications
- **web-downloader**: the report singles this out as the sharpest test of the module — "Ctrl-C mid-download should leave a resumable partial file, not a corrupt one." This directly forced the receive-oriented (not handler-based) design: because signal-handler-context code cannot safely call into `sys.fs`'s write/truncate/rename functions (not async-signal-safe operations), the *only* safe design is one where the actual file cleanup happens in ordinary application code that merely wakes up because `SignalReceiver::recv()` returned — confirming a callback-registration API would have been actively unsafe for this app's core requirement, not just less convenient.
- **chat-server**: `SIGTERM`/`SIGINT` triggering "stop accepting, notify clients, drain, exit" is a multi-step, non-trivial sequence (closing a listener, iterating live connections, sending each a notification, waiting for drains with a timeout) that must run in ordinary scheduled code with full access to the app's connection registry (behind a `sys.sync::Mutex`) — again only possible because `sys.signal` hands control back to regular code via `recv()` rather than executing this logic inside a restricted handler context. This app is also why `ignore(Signal::...)`-style `SIGPIPE` handling matters in practice: a client disconnecting mid-write must surface as a recoverable `IoError` on that connection, not terminate the whole server process.
- **cli-hangman**: a much lighter validation — "handle EOF/Ctrl-C cleanly" for a small interactive CLI — but useful precisely because it's the low-ceremony case: this confirmed the value of `on_interrupt()` as a one-line convenience wrapper, since a simple game shouldn't need to know about `Signal::Terminate` or construct an explicit signal list just to exit cleanly on Ctrl-C.

- **load-tester** (Extension round 3): re-exercises the exact `sys.signal` → `std.async::Context::with_cancel` composition `web-downloader` established, at a much higher concurrency shape (hundreds of in-flight request tasks under a fixed-duration run, versus a bounded download batch), and confirms the tier boundary rather than requiring a new one. `sys.signal` itself needed no change: `SignalReceiver::recv()` runs on one dedicated watcher (thread or task) exactly as before, its cost and latency are independent of how many other tasks the process is running, and it hands back control to ordinary code the moment Ctrl-C arrives regardless of whether that's 1 in-flight task or 500. The real question this app raises — "does the receive/poll model still compose cleanly with draining hundreds of in-flight async tasks" — resolves to: **yes, because "drain" was never `sys.signal`'s job to begin with, and this app doesn't change that.** The concrete ownership split, stated explicitly here since load-tester is the first app where getting it wrong would actually hurt: `sys.signal` owns exactly one thing, detecting that Ctrl-C arrived, via `recv()`. Everything after that — "stop issuing new requests, let in-flight ones finish (or time out), then print the partial report" — is `std.async`'s `Context`/`Scope` machinery, already exercised at connection-count scale by `chat-server`'s "close listener, notify, drain with a timeout" sequence (see that app's citation above): the watcher thread's `recv()` return simply calls the `CancelFn` from `Context::with_cancel`, the root scope's `Context` cancellation stops new `spawn` calls (the request-issuing loop checks `ctx.done()` before firing the next request), and draining in-flight requests is `std.async::timeout` wrapping the scope's join — a pattern already available in `std.async`'s existing API surface, not a new primitive. The one thing genuinely new here versus `chat-server`'s validation: load-tester's in-flight count (hundreds of concurrent requests, all started within the same short window) is large enough to make "wait for every last one, unbounded" a real risk to the tool's own promise of "still prints a valid partial report soon after Ctrl-C" — which is exactly why the drain step must be the *bounded* `timeout(...)`-wrapped join, not a bare `Scope::join`, a distinction worth stating explicitly in `std.async`'s own docs (cross-referenced there) rather than assumed. No `sys.signal` API change follows from this app; it's recorded here as confirmation that the tier split holds at this app's scale, not as a revision.
- **process-supervisor** (Round 2): validates the receive side from the supervisor's own perspective — the supervisor process itself must catch `SIGTERM`/`SIGINT` (via `register`/`recv`, exactly as `chat-server` already validated) to trigger its own graceful-shutdown sequence before forwarding termination to its children. This app also surfaced a gap in the *sending* direction: forwarding `SIGTERM` to each supervised child is not expressible through this module at all, since `sys.signal` only ever registers-for and receives signals delivered to the *current* process — there is no `send(pid, signal)` here, deliberately (see this module's Purpose). That capability was added instead as `Child::signal(sig)` in `modules/sys/process/API.md`, reusing this module's `Signal` enum as the shared vocabulary, since sending to a specific child is a process-management operation tied to the PID a `Child` handle owns, not a signal-subsystem operation. No change was needed here beyond confirming `Signal` is the right type to be reused by that neighboring module.

## Open questions / risks
This module is deliberately receive-only for the current process; process-supervisor confirmed that "send a signal to another process" is out of scope here by design, and lives on `sys.process::Child` instead (see `modules/sys/process/API.md`, "Revision (process-supervisor)") — worth stating explicitly so a future reader doesn't mistake the absence of a `send()` function here for an oversight.
Signal semantics differ meaningfully between POSIX platforms and Windows (which has no native signal delivery model, only `SetConsoleCtrlHandler`-style approximations for Ctrl-C and no real equivalent for most POSIX signals) — this API's `Signal` enum's "platform-available subset" phrasing punts on exactly how thin that subset gets on Windows, which needs a concrete resolution before this module can claim full portability.

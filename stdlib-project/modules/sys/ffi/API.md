# sys.ffi

## Purpose
C ABI interoperability: declaring extern functions/types with explicit calling convention, and — the more ambitious piece — direct ingestion of C headers so bindings don't have to be hand-transcribed or generated by an out-of-band tool.

## Design lineage
Primarily modeled on Zig's `@cImport` — the standout idea in the whole survey for this domain, ingesting a real C header at build time and producing usable declarations directly, no separate binding-generation step or checked-in generated file. Rust's `extern "C"` blocks plus the `bindgen` tool are the secondary model for the manual-declaration path (needed when no header exists, or the header uses macros/patterns `cImport`-style ingestion can't resolve), and D's `extern(C)` is the reference point for making calling-convention annotation a first-class, per-declaration type-system feature rather than a compiler-flag-level global setting.

## Proposed API
```
// Manual declaration path — always available, no header required:
extern "C" {
    fn manual_c_function(x: i32, y: *const u8) -> i32;
}
// Calling convention is part of the extern block's declaration, not ambient:
extern "stdcall" { fn windows_api_call(h: *mut c_void) -> i32; }

// Header-ingestion path — Zig-@cImport-inspired:
c_import!("mad.h", {
    include_dirs: ["/usr/include", "./vendor/libmad"],
    define: { "MAD_VERSION_MAJOR": "0" },
});
// expands to typed declarations for every function/struct/enum/macro-constant
// the header exposes, in the current module's namespace — usable directly,
// no generated-file step, no separate bindgen invocation.

// C type aliases available for both paths, matching platform C ABI sizes exactly:
type c_int = i32;  type c_uint = u32;  type c_long = /* platform-sized */;
type c_char = /* i8 or u8, platform-determined */;  type c_void = opaque;
type c_size_t = usize;

// Struct layout control, needed when hand-declaring a type that must match a C struct's memory layout:
#[repr(C)]
struct Frame { channels: c_int, rate: c_int, samples: *mut i16, len: c_size_t }

// Calling into a resolved sys.dynload symbol with an ffi-declared signature:
type DecodeFn = extern "C" fn(*const u8, c_size_t, *mut i16, c_size_t) -> c_int;
```

## Key design decisions
- Calling convention (`"C"`, `"stdcall"`, etc.) is attached per `extern` block / per function-pointer type, not set globally for a compilation unit — a program legitimately calling into both a POSIX C library and a Windows-`stdcall` system DLL in the same binary must be able to express both without a build-flag switch, matching D's per-declaration model rather than older toolchains' single ambient setting.
- `c_import!` is explicitly a *build-time* mechanism (the header is parsed and declarations generated during compilation, not at runtime) — this keeps `sys.ffi` consistent with "no hidden allocation/cost below std" in spirit, since header ingestion has zero runtime footprint, all its cost is paid once at build time, same as Zig's design.
- Every `sys.ffi` declaration and every dereference of a raw pointer obtained through it is implicitly `unsafe`, matching `sys.dynload::symbol`'s stance — the module makes no attempt to paper over C's lack of memory/type safety with a false sense of security; `#[repr(C)]` is required (not optional/inferred) on any struct meant to cross the boundary, so layout-compatibility is a decision the programmer states, not one the compiler guesses at.
- C's platform-varying integer sizes (`long` differs between LP64 Unix and LLP64 Windows) are captured as distinct `c_*` type aliases rather than the module encouraging direct use of `i32`/`i64`/`isize`, so code written against `c_long` stays correct across platforms without the programmer needing to know the underlying width at every call site.

## Validated by applications
- **mp3-player**: the sole validating app, and directly named as needing "calling into a C decoding library." This app's usage pattern — a small, fixed, known set of decoder entry points from a specific, well-documented library (e.g. libmad or a system MP3 decoder) — is a good match for the `c_import!` path if the library ships a real header, and confirmed the manual `extern "C"` path must remain fully available as a fallback: not every "C decoding library" this app might target ships a clean, `@cImport`-parseable header (some embed complex macros, conditional compilation, or non-standard extensions that defeat automatic ingestion), so the module cannot rely on header-ingestion alone. This is why both paths are first-class in the API above rather than `c_import!` being presented as a strict replacement for manual declarations.
- The app's ID3v2 tag *reading* (structured binary decoding) is explicitly handled by `std.encoding`'s binary-struct support rather than `sys.ffi` — this is a useful negative data point confirming `sys.ffi`'s scope should stay narrowly about crossing into actual foreign-compiled code, not a general-purpose binary-layout tool (that's `std.encoding`'s and `#[repr(C)]`'s job respectively, kept distinct per Principle 4's "one idiom per concern").
- **image-thumbnailer** (Round 2): the app's own "Validation note" is direct about this — since no stdlib tier decodes images, `sys.ffi`'s ergonomics "matter more than any single app in the first eleven suggested," making this the module's strongest test case yet. Compared to mp3-player's one narrow decode-frame function pointer, this app needs real bindings against `libjpeg`/`libpng`/`libwebp`-shaped C APIs: multiple structs that must cross the FFI boundary with exact C layout (`#[repr(C)]` — e.g. a JPEG decompress-info struct carrying image dimensions, color space, and row-buffer pointers), callback-style row-by-row decode APIs (a C function pointer supplied *to* the library, the inverse direction of mp3-player's "call one exported function"), and — per the app's own resize/pixel-math note — potentially `core.simd`-backed buffers crossing the same boundary if resizing is done in-language against decoded output. This is a meaningfully harder shape than mp3-player's single `extern "C" fn` case and is the first app to actually stress the `#[repr(C)]`-struct-layout and multi-function-surface parts of the design rather than just the single-function-pointer path — confirming the manual `extern "C"` block path (not just `c_import!`) needs to comfortably express a real multi-function, struct-heavy C library surface, which the sketch already allows but had not been checked against a case this shape before.
- Between mp3-player and image-thumbnailer, `sys.ffi` now has two validating apps, and no other app in the set exercises it — a smaller residual validation-breadth gap than before, still worth naming alongside `sys.process`'s (now closed by process-supervisor) and `sys.dynload`'s.

## Open questions / risks
`c_import!`'s handling of C preprocessor macros that expand to non-trivial expressions (not just constants) is an open, genuinely hard problem — Zig's own `@cImport` has known rough edges here, and this design inherits rather than solves them. Variadic C functions (`printf`-style) are also not addressed in the sketch above and need an explicit, separate mechanism if supported at all.

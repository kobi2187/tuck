# std.encoding

## Purpose
One `Codec` interface implemented uniformly by every serialization format the std tier ships — `json`, `toml`, `csv`, `base64`/`base32`/`base16`, binary struct packing, and streaming XML/Atom/RSS — so a type marshals to any format through the same calling convention.

## Design lineage
The `Codec` interface shape is modeled on Rust's `serde` (a trait-based multi-format model where `Serialize`/`Deserialize` are implemented once per type and any format is a pluggable backend, not one parser per format bolted onto each type). The module-per-format organization (`std.encoding.json`, `std.encoding.toml`, `std.encoding.xml`, …) is modeled on Go's `encoding/*` package family, which keeps each format's quirks contained without polluting a shared namespace.

## Format inclusion policy
Three new formats have been proposed for this module across two rounds — XML/RSS/Atom (`podcast-subscriber`), unified diff (`diff-patch`), YAML (`config-schema-validator`) — which is itself a finding: without a stated policy, `std.encoding`'s scope has no principled way to say no to the next one. The policy adopted here, applied retroactively to every format already in the module and prospectively to future proposals — a format belongs in `std.encoding` only if it satisfies **both**:

1. **General-purpose data interchange or durable storage, not a domain-specific mini-language.** The format must serialize arbitrary structured data — the kind of thing you'd point `Codec`'s `encode<T: Encode>`/`decode<T: Decode>` at for *any* `T` — not a representation that's only meaningful as the output of one specific tool or algorithm. `std.encoding` formats are what many independently-developed programs push arbitrary application data through; they are not the file format of one category of tool.
2. **A small, unambiguous, securely-specifiable grammar.** Parsing must not require semantic guesswork (implicit typing), and any dangerous capability the underlying spec allows must be structurally removable without forking the format into an incompatible dialect.

Applying this test:
- **JSON/TOML/CSV/base64/binary/XML** all satisfy both — general-purpose, arbitrary-`T` interchange formats with (once XML's DTD path is removed) unambiguous grammars.
- **Unified diff** (`diff-patch`) fails criterion 1, not criterion 2. Its grammar is small and unambiguous, but it isn't a serialization of arbitrary data at all — a unified diff is always and only a representation of an edit script between two specific, already-known texts, produced by one specific algorithm (LCS/Myers) and consumed by one specific operation (patch application). There is no `T` a caller would `Codec::encode` into unified-diff format the way they'd encode an arbitrary struct into JSON. **It stays out of `std.encoding`** and belongs to the extended ecosystem (or a dedicated diff/patch-focused module, if this project ever adds one — not this one). This isn't a slippery-slope concession: the identical test is why a hypothetical `.gitignore`-glob codec or a regex-syntax codec would also stay out (see `std.regex`'s own gap note on gitignore pattern-list semantics).
- **YAML** (`config-schema-validator`) fails criterion 2, not criterion 1 — see the dedicated decision below.
- **iCalendar (`.ics`, `ics-calendar-tool`) passes both criteria — a new format is added, `std.encoding.ics`.** Criterion 1: unlike unified-diff, `.ics` is a widely-used, multi-vendor interchange format (produced and consumed by independently-developed calendar apps, scheduling systems, and groupware — not the fixed output of one specific tool or algorithm); `RRULE`'s recurrence grammar is even reused outside calendaring proper. Criterion 2: iCalendar's grammar is verbose (line-folding, a flat `COMPONENT`/`PROPERTY` structure) but unambiguous — no equivalent of YAML's implicit-typing footguns, no unsafe-tag/arbitrary-object-construction history. It is therefore included, structured the same way `xml::FeedReader` sits on top of `xml::XmlReader`: `ics::IcsReader` is a focused component/property parser producing raw data (`VEvent`/`VTimezone`/`VAlarm`), and `RRULE`-to-occurrences expansion is explicitly not implemented in this module — see `mod ics` and the decision below.

## Proposed API
```
// The one interface every format implements, uniformly. T must implement core.convert's
// reflection-free Encode/Decode (hand-written or generated by std.serde-derive) OR the caller
// can use std.reflect for a schema-driven path — either way, the Codec call shape is identical.
trait Codec {
    fn encode<T: Encode>(&self, value: &T, w: &mut dyn sys::io::Writer) -> core::types::Result<(), core::error::Error>;
    fn decode<T: Decode>(&self, r: &mut dyn sys::io::Reader) -> core::types::Result<T, core::error::Error>;
}
trait Encode { fn encode_to(&self, e: &mut dyn Encoder) -> core::types::Result<(), core::error::Error>; }
trait Decode { fn decode_from(d: &mut dyn Decoder) -> core::types::Result<Self, core::error::Error> where Self: Sized; }

// Per-format entry points — all implement Codec, all take/produce any sys.io Reader/Writer.
mod json  { struct Json { pretty: bool };
            impl Json {
                // Fully dynamic decode: no target T at all, for schema-driven / self-describing-
                // document consumers where the shape isn't known until runtime — see decisions below.
                fn decode_value(&self, r: &mut dyn sys::io::Reader)
                    -> core::types::Result<std::reflect::DynValue<'static>, core::error::Error>;
            } }
mod toml  { struct Toml;
            impl Toml { fn decode_value(&self, r: &mut dyn sys::io::Reader)
                -> core::types::Result<std::reflect::DynValue<'static>, core::error::Error>; } }
mod csv   { struct Csv { delimiter: u8, has_header: bool }; }
mod base  { fn encode64(bytes: &[u8]) -> alloc::string::String;
            fn decode64(s: &str) -> core::types::Result<alloc::vec::Vec<u8>, core::error::Error>;
            // base32 / base16 mirror this pair }
mod binary { struct Binary { endian: core::num::Endian }; }  // fixed-layout struct packing

// XML/Atom/RSS: streaming-only, DTD/external-entity processing DISABLED BY DEFAULT — see decisions below.
mod xml {
    struct XmlReader<R: sys::io::Reader>;
    impl<R: sys::io::Reader> XmlReader<R> {
        fn new(r: R) -> XmlReader<R>;                       // DTD/entity expansion off; no opt-in flag exists
        fn next(&mut self) -> core::types::Result<Option<Event>, core::error::Error>;  // pull-based, one node at a time
    }
    enum Event<'a> { Start { name: &'a str, attrs: &'a [(&'a str, &'a str)] },
                      Text(&'a str), End { name: &'a str }, Eof }

    // RSS 2.0 / Atom convenience layer built entirely on XmlReader — no separate parser underneath.
    struct FeedReader<R: sys::io::Reader>;
    impl<R: sys::io::Reader> FeedReader<R> {
        fn new(r: R) -> FeedReader<R>;
        fn items(&mut self) -> impl core::iter::Iterator<Item = core::types::Result<FeedItem, core::error::Error>>;
    }
    struct FeedItem { guid: alloc::string::String, title: alloc::string::String,
                       link: alloc::string::String, pub_date: alloc::string::String,
                       enclosure_url: Option<alloc::string::String> }
}

// Added for ics-calendar-tool — passes the format-inclusion policy (see that app's validation
// note, restated in Key design decisions below). A component/property parser for iCalendar
// (RFC 5545) VEVENT/VTIMEZONE/VALARM, producing raw parsed data; RRULE-to-occurrences expansion
// is NOT implemented here — it's delegated to std.chrono::Recurrence, per the "one parser, not
// two" pattern std.encoding.xml::FeedReader already established for RSS/Atom over XmlReader.
mod ics {
    struct IcsReader<R: sys::io::Reader>;
    impl<R: sys::io::Reader> IcsReader<R> {
        fn new(r: R) -> IcsReader<R>;
        // Pull-based, one VCALENDAR component at a time — mirrors xml::XmlReader's streaming
        // shape rather than materializing the whole file, for the same "don't force buffering a
        // format that doesn't need it" reason.
        fn components(&mut self) -> impl core::iter::Iterator<Item = core::types::Result<Component, core::error::Error>>;
    }
    enum Component { Event(VEvent), Timezone(VTimezone), Alarm(VAlarm) }

    struct VEvent {
        uid: alloc::string::String,
        summary: alloc::string::String,
        dtstart: std::chrono::ZonedDateTime,
        dtend: Option<std::chrono::ZonedDateTime>,
        // Raw RRULE/EXDATE/RDATE text, NOT expanded here — see decisions. The caller builds a
        // std::chrono::Recurrence via Recurrence::from_rrule(rrule, dtstart) to get occurrences.
        rrule: Option<alloc::string::String>,
        exdate: alloc::vec::Vec<alloc::string::String>,
        rdate: alloc::vec::Vec<alloc::string::String>,
        alarms: alloc::vec::Vec<VAlarm>,
        raw_properties: alloc::map::Map<alloc::string::String, alloc::string::String>,  // uninterpreted X- extensions, LOCATION, DESCRIPTION, etc.
    }
    struct VTimezone { tzid: alloc::string::String }   // resolves to std::chrono::TimeZone by IANA ID
    struct VAlarm { action: alloc::string::String, trigger: alloc::string::String, description: Option<alloc::string::String> }

    struct IcsWriter<W: sys::io::Writer>;
    impl<W: sys::io::Writer> IcsWriter<W> {
        fn new(w: W) -> IcsWriter<W>;
        // Serializes a VEvent back to text; if `recurrence` is Some, its RecurrenceRule/bound is
        // rendered to RRULE grammar text (the inverse of Recurrence::from_rrule) rather than
        // IcsWriter re-deriving RRULE syntax independently — same single-source-of-truth rule.
        fn write_event(&mut self, ev: &VEvent, recurrence: Option<&std::chrono::Recurrence>) -> core::types::Result<(), core::error::Error>;
    }
}

fn codec_for(ext_or_mime: &str) -> Option<&'static dyn Codec>;   // generic dispatch, e.g. for archive-cli's import
```

## Key design decisions
- **YAML is deliberately excluded from `std.encoding`, the same posture the report already applied to `std.gui`'s exclusion — a formal "why not," not silence.** YAML is unambiguously general-purpose data interchange (criterion 1, above, is satisfied — same category as JSON/TOML), so it is excluded on criterion 2: its ambiguity is **load-bearing to the format's own specification**, not an optional extension. The "Norway problem" (unquoted `no`/`yes`/`on`/`off`/`NO`/`Norway`-adjacent tokens silently becoming booleans instead of strings) and implicit numeric typing of version-looking strings are not edge cases in an otherwise-clean grammar — they're consequences of YAML's core type-resolution rules, present in every conformant parser. Compare XML: its dangerous mode (DTD/external-entity resolution) is a genuinely separable extension, which is *why* XML is in this module — `XmlReader` simply never implements it, keeping 100% of XML's structural-markup usefulness while removing 100% of the XXE vulnerability class, with no dialect fork. There is no equivalent safe subset of YAML to carve out the same way; the ecosystem's actual mitigation history (Python's `yaml.load` → `yaml.safe_load`) is a bolted-on workaround for an unsafe-by-default shipped design, not a clean separation of a dangerous extension from a safe core. Given that, YAML support belongs in the extended ecosystem, where a specific library can make and own that ambiguity/safety tradeoff explicitly and visibly — not in `std`, where users reasonably expect the default behavior to be the safe one, and no clean split exists to give them that here the way it did for XML.
- **git-lite validates that nested/recursive composite structures round-trip through `binary::Binary` via ordinary composition — no extension needed, one level deeper than kv-store-server's variable-length-scalar-field validation.** A git tree object is `Vec<TreeEntry>` where `TreeEntry { mode: u32, name: alloc::string::String, hash: [u8; 32] }`: the hash is a fixed-size byte array (encoded as itself, no length prefix, like any other fixed-width field), `name` is a length-prefixed string like any other `alloc.string::String` field, and the outer `Vec<TreeEntry>` is itself length-prefixed with each element's own `encode_to` called in turn via the existing generic `Vec<T: Encode>` blanket impl — `#[derive(Encode, Decode)]` on `TreeEntry` is the entire integration cost. A commit object (`CommitObject { tree: [u8; 32], parents: alloc::vec::Vec<[u8; 32]>, message: alloc::string::String, author: alloc::string::String, timestamp: i64 }`) is the same story with reference indirection — `std.encoding` never needs to know a `[u8; 32]` field is semantically a content hash referencing another object; that meaning lives entirely in `std.crypto`/git-lite's own code, not the codec. This confirms `binary::Binary`'s existing shape already covers "structured records referencing other records by hash," which was this app's stated stress point — it needed exactly the generalization kv-store-server already forced (variable-length fields), applied one level deeper (variable-length lists of variable-length-field structs), not a new codec feature.
- **`decode_value` (JSON/TOML only) decodes straight into `std.reflect::DynValue` with no target type at all**, using `DynValue`'s new `Map` variant (see `modules/std/reflect/API.md`) for objects/tables — added for `config-schema-validator`, whose config file and externally-supplied JSON-Schema file (schemas are themselves JSON) both need to be walked generically at runtime with no compile-time-known Rust type on either side. This is the mirror image of the CSV typed-decode-only rule below, and deliberately so: CSV has no native type system to decode against, so untyped decode there is a silent-corruption risk (`"007"` guessed as `7`); JSON and TOML *are* self-describing enough that preserving their native shape (string vs. number vs. bool, object vs. array) via `decode_value` is exactly the correct, un-lossy behavior a schema validator needs, not a foot-gun. `binary::Binary` and `xml` don't get a `decode_value`: binary has no self-describing schema to decode blind against, and `xml`'s existing streaming `Event` model already serves the "no target type" use case for that format.
- **The XML codec is streaming-only and cannot be configured to expand external entities or resolve DTDs — there is no flag to turn that on.** This was a real gap surfaced by `podcast-subscriber`: the original Part IV module list had no XML at all. Given XML's XXE (XML External Entity) security history, the resolution here is XXE-safety-by-construction rather than "off by default with a caller-facing footgun switch" — `XmlReader` simply never implements DTD/entity resolution, matching the same one-`Codec`-interface contract as every other format while removing the entire vulnerability class rather than documenting it away.
- **`FeedReader` (RSS/Atom) is a thin convenience layer entirely on top of `XmlReader`**, not a second XML implementation — this is Design Principle 3 applied inside a single module: even a "special" format reuses the general streaming parser rather than embedding a private copy.
- **`ics::IcsReader` parses component/property structure only; it never expands `RRULE`/`EXDATE`/`RDATE` into occurrence dates itself — that is `std.chrono::Recurrence::from_rrule`'s job, consumed by the caller, not duplicated in the encoding layer.** This is the same "one parser, not two" boundary `xml::FeedReader` already establishes for RSS/Atom over `XmlReader`, applied on the date-math axis instead of the XML-structure axis: `VEvent.rrule` is deliberately typed as raw `Option<alloc::string::String>` (the literal `RRULE:...` text), not a pre-parsed `Recurrence`, because recurrence expansion is fundamentally date/time logic — timezone-correct, DST-transition-aware occurrence generation, per `std.chrono`'s own resolution this round — and `std.encoding` has no timezone database or DST-arithmetic of its own to do that correctly, nor should it grow one just to serve one format. A caller who wants concrete occurrence dates calls `Recurrence::from_rrule(&event.rrule.unwrap(), event.dtstart)` and then `occurrences_between` on the result; `IcsWriter::write_event` takes the same relationship in reverse (an `Option<&Recurrence>` it renders to `RRULE` text) rather than independently re-deriving RRULE syntax from scratch, so there is exactly one place in the design that understands RRULE grammar in either direction.
- **CSV's type inference is explicitly *not* automatic** — `Csv::decode` into a typed struct uses the field's declared type (via `Decode`) to parse each column, and untyped decode (`decode::<Vec<Vec<String>>>`) never guesses numeric vs. string. `doc-convert-tester`'s round-trip harness is exactly the app that would expose silent type-guessing bugs (`"007"` becoming `7`), so CSV was made the one format where the caller must state the shape rather than infer it — a deliberate, documented divergence in calling convention that Principle 4 would otherwise discourage, justified because CSV alone among these formats has no native type system to decode against.
- Every format is streaming-first (`sys.io::Reader`/`Writer`, not `&[u8]`/`String`) — `json`/`toml` also expose an `alloc.string`-backed convenience wrapper for small in-memory documents, but the primitive is the streaming one, matching `std.archive`'s and `std.compress`'s "no whole-file buffering" requirement.
- **Clarification forced by kv-store-server:** "fixed-layout struct packing" (this module's `Purpose` line for `binary::Binary`) reads as if only fixed-width fields are supported, which would not work for a WAL record's variable-length key/value bytes — that reading is not what the design means. `binary::Binary` implements the same `Codec`/`Encode`/`Decode` contract every other format does: a `Vec<u8>`/`String` field is encoded through *that type's own* `Encode` impl, which for the binary backend means a length prefix followed by the bytes, exactly the way `json`/`toml` encode a variable-length field as a length-delimited construct in their own syntax. "Fixed-layout" describes the *field order and tagging* (no self-describing schema embedded per-record, unlike JSON) — not a constraint that every field must be a compile-time-fixed size. A WAL record type (`enum WalOp { Set { key: Vec<u8>, value: Vec<u8>, expires_at: Option<i64> }, Del { key: Vec<u8> }, ... }`, `#[derive(Encode, Decode)]`) round-trips through `binary::Binary` with no bespoke framing code, the same way `secrets-vault`'s vault header and `todo-cli`'s task database already do — this app is the first to need variable-length fields in that path, and it works without change.

## Validated by applications
- **podcast-subscriber**: the originating case for `std.encoding.xml` — `FeedReader::items()` is consumed as a lazy iterator so a feed poll can stop early once known GUIDs are seen, and the DTD-disabled-by-default design was validated specifically because feed URLs are untrusted, remote, attacker-influenceable input, exactly the threat model XXE protections exist for.
- **doc-convert-tester**: the purpose-built exercise for the shared `Codec` interface — its round-trip harness iterates `codec_for` generically across json/toml/csv, which is what forced CSV's typed-decode-only rule above; also the app that most exercises `base` module correctness for embedded binary blobs surviving format round-trips.
- **secrets-vault**: uses `binary::Binary` (fixed-layout struct packing) for the on-disk vault header (version, KDF params, nonce) ahead of the AEAD-encrypted payload, and `json::Json` for the decrypted contents — validates that the binary and json codecs share enough of the `Encode`/`Decode` contract that the same vault-entry type can, in principle, target either.
- **todo-cli**: uses `json::Json` for import/export and a `binary::Binary`-packed format for the local task database itself (through the same `Codec` trait, per the app's own note that storage and wire format should not require different APIs) — validates the "same interface for durable local storage, not just wire transfer" claim.
- **kv-store-server**: the first app to pack variable-length fields through `binary::Binary` (WAL records: a command tag plus variable-length key/value byte strings, versus the fixed-shape headers `secrets-vault`/`todo-cli` exercised) — see the clarification above. Also the app that most directly exercises `binary::Binary` as a genuinely high-frequency append target (one encode call per mutating command, not an occasional whole-file write), which is a `std.encoding` concern about call-frequency rather than format correctness; the actual fsync/append-cost question belongs to `sys.fs` and is out of this module's scope, but is worth naming here since it's the reason a per-record `binary::Binary::encode` call needs to stay allocation-light on the hot path, same spirit as `json`/`toml`'s existing streaming-first decision above.
- **git-lite**: the originating case for the nested/recursive `binary::Binary` composition decision above (`TreeEntry`/`CommitObject` referencing other objects by content hash) — see decision text. Note this app is a "contrast case" for hashing specifically, not encoding: `std.encoding` packs the bytes, `std.crypto` produces the SHA-256 content-address, `core.hash` produces the unrelated fast in-memory `alloc.map` key hash for the commit-graph traversal — three different concerns that happen to look similar because they all involve "a hash," which is exactly the confusion risk this app's own profile names.
- **diff-patch**: the forcing case for the Format inclusion policy above and for the explicit unified-diff exclusion decision — diff-patch's unified-diff parsing/generation is resolved as **out of scope for `std.encoding`**; the app implements its own small hunk-header/context-line parser (built on `core.iter`/`alloc.string`, not a `Codec`), which is consistent with this being the app's own stated purpose ("the purest algorithmic app in the set").
- **config-schema-validator**: the forcing case for the YAML exclusion decision and for `decode_value`/`DynValue::Map` — the app decodes both the TOML/JSON config under test and the JSON-Schema schema file via `decode_value`, then walks the two `DynValue` trees together (see `modules/std/reflect/API.md` for the validation-walk details); this is the first app whose primary `std.encoding` use is "decode into a shape-preserving generic tree," not "decode into a known `T`."
- **ics-calendar-tool**: the originating case for `std.encoding.ics` — `icstool list`/`icstool conflicts` consume `IcsReader::components()` to pull `VEvent`s (and their nested `VAlarm`s, and any standalone `VTimezone` components used to resolve `TZID` references to `std.chrono::TimeZone`) lazily from a `.ics` file, then hand each event's raw `rrule`/`dtstart` straight to `std.chrono::Recurrence::from_rrule` for expansion — validating the parser/recurrence split described above holds end-to-end, not just in principle. `icstool add` exercises the write path: it builds a `VEvent` and a `Recurrence` from CLI flags and calls `IcsWriter::write_event`, confirming the same `Recurrence` type round-trips through both directions of the codec with no format-specific recurrence representation living in `std.encoding` itself.
- **math-toolkit-cli**: exercises `json::Json` for the currency rate table (`mtk fx --rate-file rates.json`, a small in-memory document via the `alloc.string`-backed convenience wrapper) and `csv::Csv` for `mtk stats data.csv --column price` — both are straightforward uses of already-validated paths (`doc-convert-tester` for the `Codec` interface generally, and specifically for CSV's typed-decode-only rule) with one reinforcement worth recording: the CSV column is decoded field-by-field as `Decimal` (via `Decode`), not `f64`, for the same reason `doc-convert-tester`'s round-trip cells are — a price column silently going through binary-float parsing would reintroduce exactly the rounding drift `std.math`'s `Decimal` exists to prevent, and CSV's typed-decode requirement (the caller states the target type) is what makes that the natural, unforced outcome rather than something the app has to work around.

## Open questions / risks
Whether a future opt-in, explicitly-named "trusted XML" mode (DTD resolution enabled, for closed/internal document pipelines that legitimately need it) belongs in `std.encoding.xml` under a loud, separately-named type (e.g. `TrustedXmlReader`) or should be pushed entirely to the extended ecosystem is unresolved; the current design errs toward never shipping the unsafe path in `std` at all.

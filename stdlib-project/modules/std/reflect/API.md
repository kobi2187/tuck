# std.reflect

## Purpose
Opt-in, per-type runtime introspection — field names, types, and values discoverable at runtime — for the (comparatively rare) cases that genuinely need schema-driven, dynamic behavior, with the metadata-generation cost paid only by types that ask for it.

## Design lineage
Explicitly framed in contrast to Go's `reflect` package, which the report calls out by name: Go's reflection metadata is generated for essentially every type whether or not any code ever calls `reflect.TypeOf` on it, so the cost (binary size, and in some runtimes memory) is ambient and unavoidable. `std.reflect` inverts that: a type carries zero reflection metadata unless it explicitly opts in (typically via a `#[derive(Reflect)]`-style annotation, generated by tooling akin to `std.serde-derive`'s macro), so the cost is visible in the type's own declaration, not a hidden tax on every type in the program.

## Proposed API
```
// A type opts in by implementing Reflect (hand-written, or generated — see std.serde-derive).
trait Reflect {
    fn type_info() -> &'static TypeInfo;             // static, computed once, never per-instance
    fn fields(&self) -> alloc::vec::Vec<FieldView<'_>>;   // only exists for struct-shaped Reflect types
}

struct TypeInfo {
    name: &'static str,
    kind: TypeKind,
    fields: &'static [FieldInfo],                     // empty for non-struct kinds
}
enum TypeKind { Struct, Enum { variants: &'static [&'static str] }, Primitive(PrimitiveKind), Collection }
struct FieldInfo { name: &'static str, type_name: &'static str, offset: usize }

struct FieldView<'a> { info: &'static FieldInfo, value: DynValue<'a> }
enum DynValue<'a> {
    Str(&'a str), Int(i64), Float(f64), Bool(bool),
    Struct(&'a dyn Reflect), Vec(alloc::vec::Vec<DynValue<'a>>), None,
    // Added for config-schema-validator: a fully self-describing document decoded with no
    // compiled Rust type behind it at all — contrast with Struct(&'a dyn Reflect), which
    // requires a type that opted into Reflect at compile time. Produced by
    // std.encoding::json::Json::decode_value / toml::Toml::decode_value; see Key design
    // decisions. Owns its data (parsed fresh from a Reader, nothing to borrow from), the one
    // place this enum's borrow relaxes to 'static because there's no live Rust value behind it.
    Map(alloc::vec::Vec<(alloc::string::String, DynValue<'a>)>),
}

// Dynamic access — the whole point of the module: read/write a field by name at runtime.
fn get_field<'a>(obj: &'a dyn Reflect, name: &str) -> Option<DynValue<'a>>;
fn set_field(obj: &mut dyn Reflect, name: &str, value: DynValue) -> core::types::Result<(), core::error::Error>;

// The bridge to std.encoding: a Reflect type gets Encode/Decode "for free" via a generic bridge,
// so an app can choose reflect-based (dynamic, no per-type codegen) OR serde-derive (static, generated)
// for a given type, but never both silently — see Key design decisions.
impl<T: Reflect> std::encoding::Encode for T { /* walks fields() generically */ }
```

## Key design decisions
- **`type_info()` returns a `'static` reference computed once (at first call, cached), never recomputed or allocated per instance** — introspecting a value's *shape* costs nothing beyond a pointer load after the first call, isolating the actual runtime cost to what it should be: reading/writing individual dynamic field values, not asking "what fields does this type have."
- **Opting in is per-type and explicit** (implementing `Reflect`, typically via a derive macro) — a type that never derives or hand-implements `Reflect` carries no `TypeInfo`, no vtable entry, nothing; this is the literal mechanism behind "cost is visible and chosen," directly answering the report's stated risk that Java/C#'s equivalent opt-in intentions were "partially lost to ecosystem pressure" once frameworks began assuming reflection was universally available — `std.reflect` structurally cannot be assumed available for a type that didn't ask for it, since there's no fallback blanket implementation.
- **The generic `Encode`/`Decode` bridge for `Reflect` types exists so `std.encoding`'s one-`Codec`-interface promise (Principle 4) extends to schema-driven dynamic conversion**, but a type can also implement `Encode`/`Decode` directly (hand-written or via `std.serde-derive`) without ever implementing `Reflect` at all — reflection is one path to serializability, not a requirement for it.
- **`DynValue` is a closed enum, not `Box<dyn Any>` with downcasting** — keeping dynamic values within a fixed, matchable set of shapes (mirroring `std.encoding`'s own value model) rather than opening up arbitrary-type dynamic dispatch, which would make `get_field`/`set_field` far harder to use safely from generic schema-driven code.

- **`DynValue::Map` was added for `config-schema-validator`, and it exposes a real limit of the rest of this module's design worth stating plainly rather than papering over.** `Reflect`/`get_field`/`set_field` are built for introspecting a *compiled, opted-in Rust type* dynamically — they presume a `T: Reflect` exists somewhere. Schema validation against a schema loaded at runtime from a JSON-Schema file has no such type on either side: the config file's shape isn't known until it's decoded, and the schema describing what shape is *allowed* is itself just data, loaded at runtime, not something any code derives against. That's a fully-dynamic-on-both-sides problem `Reflect`'s per-type opt-in model doesn't address at all — no amount of extending `get_field`/`set_field` fixes it, because there's no `&dyn Reflect` object to call them on in the first place. The resolution: `std.encoding`'s self-describing formats (`json`, `toml`) gained a `decode_value` entry point (see `modules/std/encoding/API.md`) that decodes straight into `DynValue` with no target type at all, using the new `Map` variant for objects/tables. A config file and a JSON-Schema file (schemas are themselves JSON) both decode into ordinary `DynValue` trees this way, and schema validation becomes a generic recursive walk comparing one `DynValue` tree against another — expressible entirely with this one added enum variant plus ordinary pattern-matching application code, not a new stdlib primitive.
- **This module deliberately does not bake in JSON-Schema's specific vocabulary** (`"type"`, `"minimum"`, `"enum"`, `"required"`, …) as first-class `std.reflect` API. Interpreting *what a schema document means* is domain logic belonging to `config-schema-validator` itself (or a small dedicated library), the same way `std.encoding` parses XML generically without knowing anything about RSS's specific element vocabulary — that's `FeedReader`'s job, a layer above the generic parser. `std.reflect`'s contribution stops at making both documents walkable as generic trees; it does not know or care what "valid" means for either one.

## Validated by applications
- **config-schema-validator**: the forcing case for `DynValue::Map` and `std.encoding`'s `decode_value` — the app decodes both the config file and the JSON-Schema file into `DynValue` trees via `decode_value` and walks the schema tree to validate the config tree (required/optional fields, type checks, ranges, enums, nested objects/arrays), building `alloc.string`-based field-path strings (`server.tls.cert_path`) as it recurses for precise violation reporting. This is a materially different `std.reflect` use case from every prior validating app below, all of which reflect over a compiled Rust type — this is the first to reflect over a document with no Rust type behind it at all.
- **doc-convert-tester**: the module's primary consumer — the harness needs to walk an arbitrary record type's fields generically to drive it through CSV/JSON/TOML conversion without hand-writing per-format glue for every test fixture type, which is exactly `Reflect::fields()`'s job; this app is also the concrete case validating that the `Encode`/`Decode` bridge for `Reflect` types actually satisfies `std.encoding`'s `Codec` contract identically to a hand-written or `serde-derive`-generated implementation, since the harness iterates "all known codecs" against the same fixture type regardless of which serialization path backs it.
- **secrets-vault**: deliberately does **not** use `std.reflect` for the vault entry type — key-value fields (site/username/password/notes) are encoded via a hand-written `Encode`/`Decode` (or `std.serde-derive`) instead, which is a meaningful negative validation: a security-sensitive type with a small, fixed, performance-irrelevant shape has no reason to pay even the opt-in reflection cost, and the module doc explicitly recommends against using `Reflect` for any type holding secret material, since `get_field`/`DynValue` provide no zeroization guarantee the way `std.crypto`'s key types do.
- **todo-cli**: uses `std.reflect` narrowly for the JSON import/export path's generic field-by-field diffing (used by an eventual schema-migration check between database versions), while the hot-path task-storage encode/decode itself uses `std.serde-derive`-generated code — validating that a single application can mix both mechanisms per-type, per Principle 4's "one idiom" applying to the *interface* (`Codec`), not to mandating a single implementation strategy for every type.

## Open questions / risks
- Whether `set_field` should support nested-path mutation (`"address.city"`) for deeply nested schema-driven editors, or stay single-level and push composition onto the caller, is unresolved; no app in the corpus needed nested dynamic mutation, so the API above stays single-level pending a concrete forcing case.
- Whether `DynValue`'s two use cases — "borrowed view into a live compiled object" (`Struct`/pre-existing variants) vs. "freestanding decoded document" (`Map`, and any nested `DynValue` under it) — should eventually be split into two named types is unresolved; they're kept as one enum here because both need the same match-on-shape ergonomics and a document decoded via `decode_value` will simply never produce a `Struct` variant, which costs nothing today but is worth revisiting if a third fully-dynamic use case appears.
